# 第 70 课：断言取消任务完成同步清理

- 日期：2026-10-15
- 课程序号：第 70 课
- 知识点：取消协程时的 try/finally

## 用途或适用场景

在上一课取消 second 后，确认它的同步清理已经结束。

## 核心概念

可取消的 delay 在取消时结束挂起并进入 finally。cancelAndJoin 返回前会等待任务结束，因此可随后断言清理记录。本课 finally 只修改测试记录，不执行挂起清理，不吞掉取消异常。

## 最小代码或操作示例

沿用 commonTest 的依赖与第 69 课所有 import，替换测试函数：

```kotlin
@OptIn(ExperimentalCoroutinesApi::class)
@Test
fun cancellationRunsCleanup() = runTest {
    val completed = mutableListOf<String>()
    var cleaned = false
    launch { delay(100); completed += "first" }
    val second = launch {
        try {
            delay(200)
            completed += "second"
        } finally {
            cleaned = true
        }
    }
    runCurrent() // 保证 second 已进入 try/delay
    advanceTimeBy(100)
    runCurrent()
    assertEquals(listOf("first"), completed)
    assertTrue(!cleaned)
    second.cancelAndJoin()
    assertTrue(second.isCancelled)
    assertTrue(cleaned)
    advanceUntilIdle()
    assertEquals(listOf("first"), completed)
}
```

cleaned 只是本测试的清理观察记录，不参与业务状态。

## 3～5 分钟练习

将 second 的 delay 改为 300；再次运行，再临时移除 finally 中的赋值，观察哪个断言失败后恢复。

## 参考答案

延长 delay 不影响清理断言；移除赋值后 assertTrue(cleaned) 失败。completed 始终只含 first，清理完成不代表第二项业务完成。

## 与上一课的联系

继承第 68 课虚拟时间推进、第 69 课 first/second/completed 和 cancelAndJoin；本课只增加 finally 同步清理的可观察断言。下一课可比较 second 正常结束时同一清理路径。
